Open [webstatus.dev](https://webstatus.dev/), pick Baseline 2021, then Baseline 2026. Look at what moved.

- CSS has almost become a second programming language. In 2021 the news was [`:is()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:is), [`aspect-ratio`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/aspect-ratio) and flexbox [`gap`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/gap). Since then we got [`:has()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:has), typed custom properties with [`@property`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@property), [style queries](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Containment/Container_size_and_style_queries#container_style_queries) and [`sibling-index()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/sibling-index), and [`if()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/if) is already in Chromium. Some of these are about to earn their keep.
- Wasm is a long way from its MVP. Garbage collection, tail calls, exceptions - all shipped. Wasm could already hold a JavaScript string by reference; Wasm 3.0 added built-in operations on those strings. We will bump into those too.

Meanwhile the world of crutches - frameworks and devtools - moves slower than the platform under it. Maybe, just maybe, it is time to experiment with something that fits the _modern_ platform.

That was my thinking when I set out to build something fun that would replace my default tools, and see how it goes. Spoiler: I ended up with something very similar to what devtools do right now. Eccentric designs are hard to craft. But I learned a few things along the way, and I want to share them with you.

So I tried to prototype a different way to build UI. A typical app is React, some state manager, a funny component structure, maybe a design system. What can I throw away? Obviously JavaScript :) TypeScript, sorry.

On top of that, I wanted to get rid of the store that holds the state, and of a virtual DOM. And finally: if CSS is so cool, why not let it control the page instead of boring HTML rewrites?

With that in mind, here is the model:

- JavaScript is swapped for Rust. Most of the time the developer writes Rust, which obviously compiles to Wasm and lands on the page as a standalone module.
- That Rust is glued to CSS through a slim JavaScript shim.
- Everything that happens turns into something CSS can read, ideally a [CSS variable](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascading_variables/Using_custom_properties). Why mutate the HTML if we can just update CSS? In some cases we have to.
- Rendering is implicit. The code itself is pretty imperative, with functional abstractions on top. More on that later.

Now we have two worlds. Rust is nice and peaceful: every value has exactly one owner. The page is where users are having fun, and nobody owns anything.

Every time something happens on the page _or_ in the environment, it becomes an event. A click on a button looks like this:

```rust
Event::Input { key: "post:42".into(), input: Input::Toggle }
```

Events live in the Rust world and build up one loooong sequence: the log. The tiny JS shim only delivers them. The user clicks a button:

```html
<button class="like" data-on="click:toggle">like</button>
```

The shim turns that into one call across the boundary: the id of `toggle`, no row, no text.

```js
app.dispatch(id, -1, new Uint8Array())
```

On the other side it becomes `Event::Input { input: Input::Toggle, .. }` and goes to the end of the log.

But you want interactivity, right? It would be cool if something actually happened when you click the button :)

The log doesn't care. It just accumulates. To get a page update you need to, unfortunately, change some state. There is no way to get rid of state. Unfair!

To get your state, you just _fold_ the log. A plain [left fold](https://en.wikipedia.org/wiki/Fold_(higher-order_function)): `reduce` if you speak JavaScript, `foldl` if you speak Haskell. You write a function that takes the state so far and one event, and returns the next state. For the like button the whole state is one flag:

```rust
pub struct View {
    pub liked: bool,
}

pub fn step(v: View, _: u64, ev: &Ev) -> View {
    match ev {
        Event::Input { input: Input::Toggle, .. } => View { liked: !v.liked },
        _ => v,
    }
}
```

The `u64` in the middle is the event's position in the log. The like button doesn't need it, so it's ignored.

Hello, Redux 👋 Except here, keeping the history is part of the runtime's job.

The state is disposable: drop it, fold the log again, get it back. Almost. There is some fine print about checkpoints coming up. The actions are the thing we keep. Backend people have a name for this: [event sourcing](https://martinfowler.com/eaaDev/EventSourcing.html).

A log and a fold. That is the whole idea, so the toy got its name from it: [LogFold](https://github.com/HellSquirrel/stream-fold).

Note the `View` in the example. There are no stores with global state. There are views, and each one is its own fold over the same log. Want two? Fold twice, or zip them into one.

Now we need to apply the view to what the user can see. How? Step one: find who owns it. Meet our good old friend, the component.

```rust
logfold_core::component! {
    pub mod ui;
    domain Like;
    prefix like;
    inputs { toggle => Toggle }
    root { var liked: int; }
    state View;
    step = step;
    project = project;
}
```

Don't worry about all the parameters too much. The important one is `project`.

```rust
pub fn project(v: &View) -> Projection {
    Projection::new().set(ui::liked.slot(), u8::from(v.liked))
}

// simplified: the real one is sorted and batches writes
pub struct Projection {
    pairs: Vec<(Slot, f64)>,
}

// what ui::liked.slot() is for our button
Slot { target: Target::Root, kind: SlotKind::Var, name: intern("--like-liked") }
```

So `project` takes a view and turns it into a projection. A projection carries two things, many times over:

- a slot - a named place on the page. Here there is one, `ui::liked`, generated from `root { var liked: int; }` in the declaration, so a typo is a compile error.
- a number. For a yes-or-no state like ours it is 1 or 0.

The slot says where the number lands and what it becomes. For the like button:

- `target` is `Root`, the `<html>` element itself. A named target would be an element with `data-fold="name"`.
- `kind` is `Var`. The number becomes a CSS variable. Not a class, not an attribute, not a node.
- `name` is `--like-liked`: the component's prefix plus the slot's name. `liked` is a popular word, and a component usually lives on somebody else's page.

So a projection describes everything a component shows. Now we need to let the page know. Re-applying the whole thing on every click would be silly, so we don't. The host keeps the last projection it sent, compares it with the new one and ships only the pairs that changed. For the like button that is one pair. Nobody calls render. The difference _is_ the render.

And since a pair is just numbers, the border is happy.

On the page the number becomes one CSS variable: `--like-liked: 1`. That's it. Why mutate the HTML if we can just update CSS? With constructable stylesheets, the like update itself touches only CSSOM: the shim owns a tiny stylesheet with one `:root {}` rule and sets the variable there. No nodes change, no classes toggle, no attributes change. The history panel still has paperwork to display, so it updates its own DOM. Older browsers without constructable stylesheets fall back to an inline style on `<html>`. On the CSSOM path, one variable changed, and the stylesheet takes it from there:

```css
.like {
  scale: calc(1 + var(--like-liked) * .1);
  color: if(style(--like-liked: 1): #d32f2f; else: #222);
}
.like::before {
  content: if(style(--like-liked: 1): "♥ "; else: "♡ ");
}
```

Arithmetic with [`calc()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/calc) for the scale, `if()` for the rest. The variable is read right where it is needed, with no selector for the state at all. In our tests this was roughly in the same ballpark as a plain class selector. Rust never sees a heart. It doesn't know what `liked` looks like, and it shouldn't.

One catch: `if()` is Chromium-only today. In other current browsers the demo falls back to a style query on the same variable, which was a bit slower in our tests:

```css
@container style(--like-liked: 1) {
  .like { color: #d32f2f; }
  .like::before { content: "♥ "; }
}
```

<Details withBackground title="What actually crosses, and where it lands">
Every change is five numbers: which element, which row, what kind, which name, what value. A click on the like button sends exactly this:

```js
[0, -1, 0, 1, 1]
// element 0 is "root", -1 is "no row", kind 0 is a variable, name 1 is "--like-liked", value 1 is "on"
```

The shim asks for the two names once and remembers them. Then it writes the variable, and not onto `<html>`. At start-up it creates one stylesheet of its own with a single empty rule, and root variables go there:

```js
const sheet = new CSSStyleSheet()
sheet.replaceSync(':root {}')
document.adoptedStyleSheets.push(sheet)

sheet.cssRules[0].style.setProperty('--like-liked', 1)
```

This is a write to the CSS object model, not to the document. In our measurements it was about as cheap as toggling a class. The generated stylesheet registers the variable, so it has a type and a default:

```css
@property --like-liked { syntax: "<integer>"; inherits: true; initial-value: 0; }
```

A named element works the same way: its variables go into a rule on its class, so the shim never even looks the element up. Only rows, which come and go, carry their numbers themselves.
</Details>

The whole trip of one click, top to bottom:

```
click ──▶ Event::Input { input: Toggle, .. }    appended to the log
                     │
                     ▼ step
              View { liked: true }
                     │
                     ▼ project
        (Slot { Root, "--like-liked" }, 1)
                     │
                     ▼ the diff, then the shim
          :root { --like-liked: 1 }
                     │
                     ▼ stylesheet
     content: if(style(--like-liked: 1): "♥ "; else: "♡ ")
```

Not HTML, not a tree. A flat list of pairs. That's all Rust knows about the page.

## Challenges

### A memory leak with a business model

Our calculations look great, but there is a caveat. We just built a huge memory leak. The log is never cleaned up.

The present is cheap: we keep the current state and apply each new event to it once. The past is more demanding. Drag the slider backwards, and folding the whole log from the beginning every time would be too much work.

To solve this we introduce checkpoints. Since our state is a deterministic left fold, we can save it after the first `k` events and resume from there, keeping the remaining events' original indices. The law that makes this legal is one line:

```
fold(log) == fold_from(state_at(k), log[k..])   // for any k
```

We can also throw away the events before a checkpoint. Here is the fine print: that checkpoint stops being disposable. We need it, plus the remaining log, to reconstruct the state. The slider cannot visit the forgotten past, and a new fold cannot read events we no longer have. Time travel has a retention policy.

Text gets another exception. A todo's title can still point to an old event, so before deleting that event we move its text into a separate archive. That archive can keep growing, as can the app's state and the rows we hide rather than remove. We have bounded the event history, not all memory use. Garbage collection, with souvenirs.

<Details withBackground title="What if there are many folds?">
We zip them all together before we go. `zip` runs two folds over the same events in one pass and keeps a pair of states, so a checkpoint is always the state of _one_ fold. Views derived with `map` need no storage at all: they are functions of that state.
</Details>

<Details withBackground title="Time travel between checkpoints">
Checkpoints live in a B-tree, ordered by time. To show the page as it was at some moment, ask the tree for the last checkpoint before that moment, then replay the few events between the two. That is the whole slider.

A small Wasm lesson. In an earlier build, checkpoint cleanup pulled extra tree-removal code into the Wasm module through a single call to `BTreeMap::remove`. To shrink it back, we had to get rid of that one method. Instead of removing old checkpoints, we now rebuild the tree from the ones we keep. Same retained checkpoints, less machinery to ship.
</Details>

### The border

We have two worlds, and crossing the border between them sounds expensive. In our measurements, small numeric calls were cheap; converting strings was where the paperwork started. Rust's ordinary data structures live in Wasm's linear memory, an array of bytes. JavaScript can read and write that memory through typed-array views. JavaScript objects, including DOM nodes, live elsewhere: Rust can keep handles to them, but their internals do not become Rust data. So:

- Numbers need no string encoding or object serialization. That makes them useful cargo for our patches.
- Converting between a Rust `String` and a JavaScript string copies and re-encodes the contents: Rust uses UTF-8, while JavaScript exposes UTF-16 code units. Keeping a reference to an existing JS string avoids that conversion.
- Wasm can receive a host value as an `externref`. With wasm-bindgen, Rust stores a handle to that value; calling its JavaScript methods still involves host calls.
- Calling the DOM from Rust does not bypass the browser's DOM, style or layout work. Rust does not get a secret faster DOM.

Wasm 3.0 brought [JS String Builtins](https://developer.mozilla.org/en-US/docs/WebAssembly/Guides/JavaScript_builtins). Holding a JavaScript string as an `externref` was already possible. The new part is working on it through functions from the reserved `wasm:js-string` namespace: `length`, `concat`, `substring`, `equals`. The engine recognizes these imports and can optimize them without an application-written JavaScript wrapper. No trip through UTF-8 just to ask how long a JS string is. Creating or concatenating strings can still allocate, of course. The paperwork has limits.

```js
WebAssembly.instantiateStreaming(fetch('app.wasm'), imports, {
  builtins: ['js-string'],
  importedStringConstants: 's',
})
```

```wasm
(global $liked (import "s" "liked") externref)
(func $equals (import "wasm:js-string" "equals")
  (param externref externref) (result i32))
```

The second option is the fun one. With `importedStringConstants` the engine reads the import name and hands the module a ready JavaScript string. The literal still appears in the module's import metadata, but it does not need a UTF-8 copy in linear memory.

Rust can already keep a JS string without copying its contents through [`js_sys::JsString`](https://wasm-bindgen.github.io/wasm-bindgen/reference/types/str.html). Rust holds a numeric handle, and the actual reference lives in a table. Those handles can live in structs and vectors. A `Vec<JsString>` is perfectly legal; a `Vec` of bare Wasm references is a different matter.

Our current pipeline does not use the new builtins. With wasm-bindgen 0.2.128 and the corresponding js-sys 0.3.105 release, the ordinary [`JsString` bindings](https://github.com/wasm-bindgen/wasm-bindgen/blob/0.2.128/crates/js-sys/src/lib.rs) call JavaScript properties and methods. Getting `wasm:js-string` imports would take extra integration. The handles are no obstacle in principle: Wasm can look up a reference in its table and pass it to a builtin. More plumbing, then. We were trying to build a like button.

There is an [open RFC](https://github.com/rust-lang/rfcs/pull/3987) for a native Rust `externref` type. As proposed, it would be allowed in function arguments, return values and local bindings, but not inside a `Vec` or a struct. That could make direct interop easier. It does not mean Rust has to wait for the RFC to keep a JS string alive.

LogFold currently does the boring thing: the log keeps Rust-owned text, so its core can run outside a JavaScript host too. Names are fetched and cached by the shim, and patches carry numeric IDs. Text the user typed enters the log as UTF-8 bytes; a text patch carries the event's position, and the shim asks for a JavaScript string when a row needs to show it. That conversion still costs us. It is a choice in this implementation, not a law of Wasm.

### The bundle

Another problem is the bundle size. Rust compiles ahead of time, so there is no runtime to ship, right? Not quite. There is no garbage collector, but you still pack your own allocator, your own panic messages and your own collections. Here is the current like runtime breakdown, using the asset definition above and Brotli quality 11 (decimal KB):

```
the Wasm module         19.01 KB
the JS shim              5.79 KB
wasm-bindgen glue        2.27 KB
the generated CSS        0.10 KB
                        --------
                        27.17 KB
```

A like runtime that weighs 27 KB, and 84 KB unbrotlied. In JavaScript it is a few lines. So where does it all go? Earlier [twiggy](https://rustwasm.github.io/twiggy/) profiles of named, uncompressed Wasm builds pointed at the host and exports, framework machinery, collections, panic formatting and the allocator. Those profiles describe the Wasm module, not shares of the compressed total above.

The like-button logic is a tiny part of its own bundle. Most of the weight is the machinery we brought along to flip one flag. Exact percentages depend on the build; the embarrassment is remarkably stable.

Here is what we did about it:

- **Swapped the allocator.** In our earlier Wasm build, the default allocator, dlmalloc, contributed about 8 KB of uncompressed code. Our apps allocate small, short-lived things, so we use [talc](https://github.com/SFBdragon/talc), which contributed about half of that in the measured build.
- **Threw out the standard sort.** In an earlier build, one call to `sort` added about 17 KB to the uncompressed Wasm module. A hand-written merge sort costs a fraction of that.
- **Less formatting.** `assert_eq!` looks innocent, but when it fails it prints both values, and that links the number formatting code. We use a plain `assert!` with a fixed message.
- **Lists are opt-in.** The list machinery sits behind a trait object, so a like button does not pay for rows it does not have.
- **The usual compiler flags.** `lto`, one codegen unit, `panic = "abort"`, and `wasm-opt -Oz` on top. One surprise: `opt-level = "z"` made the file smaller and the _compressed_ file bigger, so we kept the default.

There is also a build without wasm-bindgen at all: plain `extern "C"` functions and numbers. The current raw Wasm module is 52.18 KB uncompressed and 17.85 KB Brotli, versus 54.74 KB and 19.01 KB for the bindgen module. It also needs no generated bindgen JS, which is another 2.27 KB Brotli in the normal build. These are module and glue comparisons; the raw path has its own loader, so they are not whole-page totals.

### Text

The next problem is text. We've ignored it for a while, but this is where the dynamics we mentioned before start shooting us in the foot. A title is whatever the user typed. It is not a number, and no stylesheet knows it in advance.

Technically CSS can print a string from an attribute. But generated content cannot be selected or copied, and a todo you can't copy is a sad todo. So this time there is no way around it: we need to mutate the HTML.

Here is how. First, an input can carry text. One word in the declaration, and the field's value travels with the event, once, as bytes:

```rust
inputs { add: text => Add, toggle: index => Toggle }
```

Press Enter, and `Add("buy milk")` lands in the log. Now the trick: the projection still carries only numbers. The title's number is the place of that event in the log.

```rust
// item.id is where its Add event sits in the log
.set(ui::item::title.at(row), item.id as f64)
```

So the patch says "row 0, title, 7". The shim asks Rust for the text of event 7 and writes it into the row as a real text node:

```js
row.querySelector('[data-text="title"]').textContent = app.text(7)
```

The string crosses the border on the way in, with the event, and on the way out, when a row has to show it. Everything in between is numbers. And the slider gets the titles for free. The text lives in the log, so going back in time brings the right words back.

### New rows

After the text is saved, we need a new element to put it in. We do it in a quite standard way, in the JS shim. The page carries a `<template>` with one row in it:

```html
<ul>
  <template data-fold="item">
    <li class="item">
      <label>
        <input class="check" type="checkbox" data-checked="done" data-on="click:toggle">
        <span class="title" data-text="title"></span>
      </label>
    </li>
  </template>
</ul>
```

On the Rust side a row is a family of slots, and nothing more:

```rust
family item { class present; checked done; attr n: int; text title; }
```

Note what is missing: there is no "create a row" command. Rust just keeps projecting numbers: "row 3 is present, its number is 4, its title is event 12". When a patch names a row the shim has never seen, the shim makes one:

- It collects everything the patch says about the new row: classes, attributes, the title.
- It renders the row from the template as a string, with those first values already in it.
- All new rows of one patch go in with a single `insertAdjacentHTML`. A thousand rows is one parse, not a thousand clones.
- It remembers the element under its row number, so later writes go straight to it.

The title is the exception. It is set as text after the row is in, never as HTML, so a todo called `<script>` stays a todo.

Rows are never removed. A row the state no longer mentions loses its `present` class, and the stylesheet hides it.

### The checkbox

The second place where we touch the HTML is the checkbox. Its state is a property of a native element, not something CSS can set. So there is a slot for it:

```rust
family item { class present; checked done; attr n: int; text title; }
```

The shim writes `checked` on the input marked `data-checked="done"`, and the look comes back to CSS through [`:checked`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:checked):

```css
.item:has(.check:checked) .title { text-decoration: line-through; }
```

How does Rust know which box was clicked? A click carries the row's index with it. That is what `toggle: index` in the declaration means. Rust flips the item in that row.

<Details withBackground title="A confession about keys">
Our rows are identified by position. A click says "toggle row 2", and Rust flips the third item: indices start at zero. This works for our app because we never remove an item or insert one in the middle.

A click while viewing the past still applies to the current head of the log, then the page jumps back to the present. It does not create a new branch of history. If we allowed removals or insertions in the middle, historical row 2 could name a different todo at the head, and we could toggle the wrong one. The fix is the usual one: give every row a stable key. We even have one for free, the place of its `Add` event in the log. Hello, React keys.
</Details>

### A row that knows its number

Every todo has a number in front of it. The idea: a row number is pure presentation, so it should never cross the border. Let CSS count.

The first version used a [CSS counter](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Counter_styles/Using_counters). It works, but the numbering depends on what came before. A change near the top can leave the browser with quite a lot to reconsider below it.

Then `sibling-index()` reached Baseline: a function that tells an element which child it is. It looked like the perfect fit. Each row knows its own number, no chain.

```css
/* minus one, because the <template> is a sibling too */
.item::before { counter-reset: n calc(sibling-index() - 1); content: counter(n); }
```

So we measured it in Chrome. On a list of ten thousand rows, appending one more got about four times slower than with the old counter. Apparently knowing your own number still involves some family bureaucracy when the list changes. Whatever the browser was reconsidering, the newest CSS function in this post came last in this test.

What changed in the end is boring. The row's number became one more number from Rust: an attribute, written once when the row appears and printed as is with [`attr()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/attr).

```rust
family item { class present; checked done; attr n: int; text title; }
```

```css
.item::before { content: attr(data-n); }
```

One extra write per row, nothing after that for our append-only list, and in this test reasonably close to having no numbers at all. The dull solution won.

And that is our second app. Hooray, the TODO list! Or, to be precise, the 92 KB todo runtime. 30 KB brotlied, to be fair, about 2.4 KB more than the like runtime before rounding. Same asset-counting rules as before. It adds. It ticks. It cannot remove an item, it cannot edit one, and a reload loses everything, because the log lives in memory. That is the whole feature list.

### Time

To make the app work we need one more concept: time. A like button doesn't care what time it is. A robot does.

Rust never reads a clock. Time is just one more event in the log, `Event::Tick { ms: 250 }`, and the page owns the clock. While the state says "running", a small loop on the page appends a tick a few times a second:

```js
if (running) host.frame(1000 / fps)
```

`frame(250)` advances virtual time by 250 ms. The logged `Tick.ms` is the cumulative timestamp: 250, 500, 750, and so on. Frames also record what the simulated sensors report.

This is why the slider works on Brunhilda too. The same recorded events, including commands and senses, in the same order give the same robot, every time. Even the speed is state: faster and slower are ordinary inputs, like a click on the like button.

### A brain, a studio, a world

To make Brunhilda move, we wrote a small crate for her brain. It is a fold, like everything else here: events in, a state out. Her events are commands (start, dock, stop), senses (a bump, "the human is at this cell") and ticks. That is her whole vocabulary.

The same framework builds the rest: the controls of the studio, and the simulated world - the room, the furniture, me.

But notice something interesting about how our boundary fits the separation of concepts. A good part of this post was about one border: Rust on one side, the page on the other, numbers in between. Rust never touches the HTML. It says what should be shown, as data, and somebody else makes it so.

Brunhilda's brain sits behind exactly the same kind of border. She never touches a motor. Events come in, and what she wants goes out as data: a heading for the next frame, an emergency stop. The world makes it so. She knows nothing about the page, and she does not know that her world is simulated either. She lives in the Matrix! Swap the simulated room for real wheels and her crate does not change. Nobody has tried, to be fair.

So the border we fought with for performance turns out to be the place where the concepts separate anyway. What to do lives on one side, how it gets done on the other. For a UI the other side is CSS. For a robot it is the world.

### Effects

Her emergency stop is an effect, and effects deserve a post of their own. The short version: a fold never performs the effect itself. It only says what it wants, as a value: "this request should be in flight", "the motors should be stopped". The host compares that with what it has already started and records a `Started` event before handing off the work. If the effect has an answer, that comes back as another event. The emergency stop is fire-and-forget; it has no answer to wait for.

Replay reads those recorded events to reconstruct state. It does not send the request again. Dragging a slider should not accidentally order a second pizza.

We have a networked like-button model too, tested against a simulated server by a fuzzer that tried hard to break it. Wiring it to a real network executor is another job. But not today.

And that is our third app. Hooray, the ROBOT! Or, to be precise, the 144 KB robot runtime. 46 KB brotlied, to be fair, including its imported manifest and using the same asset-counting rules. She cleans. She docks. She stops when told. With the naive policy she still attacks me. That is the whole feature list.

## Wrapping up

I prototyped the first version with my LLM agents very quickly, and then did tons of iterations to fix bugs and improve things. Along the way I wrote a fuzzer, brought in a bundle analyzer and standardized the way I benchmark the app.

Of course, this is still a long way from a full-featured framework. Three demos and a robot with questionable manners do not quite get us there. But the results are promising.

The approach turned out to be less crazy than I expected. Performance looks good in the tests so far, and the bundle sizes seem acceptable to me for experimenting further. Even after spending several paragraphs making fun of the like button.

The other surprise was how much I enjoyed writing components in Rust. That alone is a good reason to keep playing with it. I think I will, and see where it goes.
