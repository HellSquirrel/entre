Open [webstatus.dev](https://webstatus.dev/), pick Baseline 2021, then Baseline 2026. Look at what moved.

- CSS has almost become a second programming language. In 2021 the news was [`:is()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:is), [`aspect-ratio`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/aspect-ratio) and flexbox [`gap`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/gap). Since then we got [`:has()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:has), typed custom properties with [`@property`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@property), [style queries](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Containment/Container_size_and_style_queries#container_style_queries) and [`sibling-index()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/sibling-index), and [`if()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/if) is already in Chromium. We will use every one of them below.
- Wasm is a long way from its MVP. Garbage collection, tail calls, exceptions - all shipped. Wasm 3.0 can even hold a JavaScript string by reference. We will bump into that one too.

Meanwhile the world of crutches - frameworks and devtools - moves slower than the platform under it. Maybe, just maybe, it is time to experiment with something that fits the _modern_ platform.

That was my thinking when I set out to build something fun that would replace my default tools, and see how it goes. Spoiler: I ended up with something very similar to what devtools do right now. Eccentric designs are hard to craft. But I learned a few things along the way, and I want to share them with you.

So I tried to prototype a different way to build UI. A typical app is React, some state manager, a funny component structure, maybe a design system. What can I throw away? Obviously JavaScript :) TypeScript, sorry.

On top of that, I wanted to get rid of the store that holds the state, and of any kind of virtualization. And finally: if CSS is so cool, why not let it control the page instead of boring HTML rewrites?

With that in mind, here is the model:

- JavaScript is swapped for Rust. Most of the time the developer writes Rust, which obviously compiles to Wasm and lands on the page as a standalone module.
- That Rust is glued to CSS through a slim JavaScript shim.
- Everything that happens turns into something CSS can read, ideally a [CSS variable](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascading_variables/Using_custom_properties). Why mutate the HTML if we can just update CSS? In some cases we have to.
- Rendering is implicit. The code itself is pretty imperative, with functional abstractions on top. More on that later.

Now we have two worlds. Rust is nice and peaceful: every value has exactly one owner. The page is where users are having fun, and nobody owns anything.

Every time something happens on the page _or_ in the environment, it becomes an event. A click on a button looks like this:

```rust
Event::Input { key: "post:42".into(), input: Input::Toggle }
```

Events live in the Rust world and build up one loooong sequence: the log. The tiny JS shim only delivers them. The user clicks a button:

```html
<button class="like" data-on="click:toggle">like</button>
```

The shim turns that into one call across the boundary: the id of `toggle`, no row, no text.

```js
app.dispatch(id, -1, new Uint8Array())
```

On the other side it becomes `Event::Input { input: Input::Toggle, .. }` and goes to the end of the log.

But you want interactivity, right? It would be cool if something actually happened when you click the button :)

The log doesn't care. It just accumulates. To get a page update you need to, unfortunately, change some state. There is no way to get rid of state. Unfair!

To get your state, you just _fold_ the log. A plain [left fold](https://en.wikipedia.org/wiki/Fold_(higher-order_function)): `reduce` if you speak JavaScript, `foldl` if you speak Haskell. You write a function that takes the state so far and one event, and returns the next state. For the like button the whole state is one flag:

```rust
pub struct View {
    pub liked: bool,
}

pub fn step(v: View, _: u64, ev: &Ev) -> View {
    match ev {
        Event::Input { input: Input::Toggle, .. } => View { liked: !v.liked },
        _ => v,
    }
}
```

The `u64` in the middle is the event's position in the log. The like button doesn't need it, so it's ignored.

Hello, Redux 👋

But our system works the other way round. The state is disposable: drop it, fold the log again, get it back. The actions are the thing we keep, all of them. Backend people have a name for this: [event sourcing](https://martinfowler.com/eaaDev/EventSourcing.html).

A log and a fold. That is the whole idea, so the toy got its name from it: [LogFold](https://github.com/HellSquirrel/stream-fold).

Note the `View` in the example. There is no global state. There are views, and each one is its own fold over the same log. Want two? Fold twice, or zip them into one.

Now we need to apply the view to what the user can see. How? Step one: find who owns it. Meet our good old friend, the component.

```rust
logfold_core::component! {
    pub mod ui;
    domain Like;
    prefix like;
    inputs { toggle => Toggle }
    root { class liked as var; }
    state View;
    step = step;
    project = project;
}
```

Don't worry about all the parameters too much. The important one is `project`.

```rust
pub fn project(v: &View) -> Projection {
    Projection::new().set(ui::liked.slot(), u8::from(v.liked))
}

// simplified: the real one is sorted and batches writes
pub struct Projection {
    pairs: Vec<(Slot, f64)>,
}

// what ui::liked.slot() is for our button
Slot { target: Target::Root, kind: SlotKind::Class, name: intern("like-liked") }
```

So `project` takes a view and turns it into a projection. A projection carries two things, many times over:

- a slot - a named place on the page. Here there is one, `ui::liked`, generated from `root { class liked as var; }` in the declaration, so a typo is a compile error.
- a number. For a yes-or-no state like ours it is 1 or 0.

The slot says where the number lands and what it becomes. For the like button:

- `target` is `Root`, the `<html>` element itself. A named target would be an element with `data-fold="name"`.
- `name` is `like-liked`: the component's prefix plus the slot's name. `liked` is a popular word, and a component usually lives on somebody else's page.
- `as var` is the important part. It says: show this state to the stylesheet as a CSS variable, `--like-liked`.

So a projection describes everything a component shows. Now we need to let the page know. Re-applying the whole thing on every click would be silly, so we don't. The host keeps the last projection it sent, compares it with the new one and ships only the pairs that changed. For the like button that is one pair. Nobody calls render. The difference _is_ the render.

And since a pair is just numbers, the border is happy.

On the page the number becomes one CSS variable: `--like-liked: 1`. That's it. Why mutate the HTML if we can just update CSS? No element is created, moved or rewritten. The markup is exactly as it was written. One variable changed, and the stylesheet takes it from there:

```css
.like {
  scale: calc(1 + var(--like-liked) * .1);
  color: if(style(--like-liked: 1): #d32f2f; else: #222);
}
.like::before {
  content: if(style(--like-liked: 1): "♥ "; else: "♡ ");
}
```

Arithmetic with [`calc()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/calc) for the scale, `if()` for the rest. The variable is read right where it is needed, with no selector for the state at all. In our tests this costs the same as a plain class selector. Rust never sees a heart. It doesn't know what `liked` looks like, and it shouldn't.

One catch: `if()` is Chromium-only today. For everyone else the demo falls back to a style query on the same variable, which is plain 2026 CSS and a bit slower:

```css
@container style(--like-liked: 1) {
  .like { color: #d32f2f; }
  .like::before { content: "♥ "; }
}
```

<Details withBackground title="What actually crosses, and how it becomes a variable">
Every change is five numbers: which element, which row, what kind, which name, what value. A click on the like button sends exactly this:

```js
[0, -1, 3, 1, 1]
// element 0 is "root", -1 is "no row", kind 3 is a state, name 1 is "like-liked", value 1 is "on"
```

The shim asks for the two names once and remembers them. For a state it flips one class on the element, and a two-line stylesheet, generated from the declaration at build time, turns that class into the variable:

```css
@property --like-liked { syntax: "<integer>"; inherits: true; initial-value: 0; }
.like-liked { --like-liked: 1; }
```

Why the extra hop? A class is the cheapest hook a stylesheet has, and that starts to matter when there are thousands of rows. Plain numbers, like the robot's position, skip the hop: the shim sets them as variables directly with `style.setProperty`.
</Details>

The slider works the same way. Moving it back is the same diff in the other direction, which is why it drives the real button and not a copy of it.

The whole trip of one click, top to bottom:

```
click ──▶ Event::Input { input: Toggle, .. }    appended to the log
                     │
                     ▼ step
              View { liked: true }
                     │
                     ▼ project
          (Slot { Root, "like-liked" }, 1)
                     │
                     ▼ the diff, then the shim
               --like-liked: 1
                     │
                     ▼ stylesheet
     content: if(style(--like-liked: 1): "♥ "; else: "♡ ")
```

Not HTML, not a tree. A flat list of pairs. That's all Rust knows about the page.

That was the basics. Now the fun part.

## Challenges

### A memory leak with a business model

Our calculations look great, but there is a caveat. We just built a huge memory leak. The log is never cleaned up.

On top of that, sometimes we don't want to fold at all. We want our new shiny state right now, and folding the whole log to get it is too much work.

To solve this we introduce checkpoints. Since our state is a left fold, we can freeze it at any point and throw away the sequence before it. The law that makes this legal is one line:

```
fold(log) == fold_from(state_at(k), log[k..])   // for any k
```

<Details withBackground title="What if there are many folds?">
We zip them all together before we go. `zip` runs two folds over the same events in one pass and keeps a pair of states, so a checkpoint is always the state of _one_ fold. Views derived with `map` need no storage at all: they are functions of that state.
</Details>

<Details withBackground title="Time travel between checkpoints">
Checkpoints live in a B-tree, ordered by time. To show the page as it was at some moment, ask the tree for the last checkpoint before that moment, then replay the few events between the two. That is the whole slider.

A small Wasm lesson. After we added the cleanup, every bundle grew by 2.6 KB. The culprit was a single call to `BTreeMap::remove`: nothing else in the app removed anything from a tree, so the whole removal code came along just for it. To shrink the bundle back, we had to get rid of that one method. Instead of removing old checkpoints, we now rebuild the tree from the ones we keep. Same tree, same result, and the 2.6 KB are gone.
</Details>

### The border

We have two worlds, and crossing the border between them sounds expensive. A quick measurement says otherwise: crossing is cheap, unless you carry a string. Here is why. Rust lives in its own linear memory, one big array of bytes. JavaScript cannot point into it, and Rust cannot hold a DOM node. So:

- A number crosses almost for free. A call with a number costs about the same as a plain JS call.
- A string is copied and re-encoded, UTF-8 on one side, UTF-16 on the other. That is many times the price of a number.
- An object does not cross at all. It becomes a handle in a table, and every touch is one more call across the border.
- The DOM costs the same from both sides. The call itself is the expensive part, so there is no prize for making it from Rust.

However, for strings this is about to stop being true. Wasm 3.0 brought [JS String Builtins](https://developer.mozilla.org/en-US/docs/WebAssembly/Guides/JavaScript_builtins). A module can now hold a JavaScript string as an `externref` - a reference, not a copy - and work on it with functions from the reserved `wasm:js-string` namespace: `length`, `concat`, `substring`, `equals`. The engine knows these imports and inlines them. No glue, no re-encoding.

```js
WebAssembly.instantiateStreaming(fetch('app.wasm'), imports, {
  builtins: ['js-string'],
  importedStringConstants: 's',
})
```

```wasm
(global $liked (import "s" "liked") externref)
(func $equals (import "wasm:js-string" "equals")
  (param externref externref) (result i32))
```

The second option is the fun one. With `importedStringConstants` the engine reads the import name and hands the module a ready JavaScript string. The string "liked" never exists as bytes on the Rust side at all.

Sadly, none of it works for us yet. But why? A reference to a JavaScript string is not bytes. It cannot live in linear memory, that is the whole point of it. And everything in Rust lives in linear memory: a struct field, a `Vec`, a closure. Rust simply has no type for "a thing that is not in memory".

So wasm-bindgen fakes it. It keeps the real references in a table and gives Rust a number, an index into that table. A number is not something you can pass to `wasm:js-string`. There is an [open RFC](https://github.com/rust-lang/rfcs/pull/3987) to add a real `externref` type to Rust. Even then it will only be allowed in function arguments, return values and local variables. You still won't be able to put one in a `Vec`, so the log could never hold it.

So LogFold does the boring thing: a string crosses once. A name crosses the first time it is used and becomes a two-byte id. Text the user typed crosses into the log once. After that the patches carry only its place in the log, and the shim fetches the string when a row has to show it.

### The bundle

Another problem is the bundle size. Rust compiles ahead of time, so there is no runtime to ship, right? Not quite. There is no garbage collector, but you still pack your own allocator, your own panic messages and your own collections. Here is how heavy our like button is, compressed with brotli:

```
the Wasm module         19.0 KB
the JS shim              5.3 KB
wasm-bindgen glue        2.3 KB
the generated CSS        0.1 KB
                        -------
                        26.7 KB
```

A like button that weighs 27 KB, and 82 KB unbrotlied. In JavaScript it is a few lines. So where does it all go? Let's ask [twiggy](https://rustwasm.github.io/twiggy/):

```
wasm-bindgen glue and exports        18%
the framework core                   16%
the host: log, checkpoints, patches  15%
B-tree code                          15%
panic messages and formatting        14%
the allocator                         9%
read-only data                        7%
everything else                       5%
the like button itself                1%
```

The like button is 1% of its own bundle. The rest is mostly a fixed price that every app pays, however small.

Here is what we did about it:

- **Swapped the allocator.** Rust's default allocator on Wasm, dlmalloc, is about 8 KB of code. Our apps allocate small, short-lived things, so we use [talc](https://github.com/SFBdragon/talc), which is about half of that.
- **Threw out the standard sort.** One call to `sort` pulled 17 KB of the standard library into every bundle. A hand-written merge sort costs a fraction of that.
- **No formatting.** `assert_eq!` looks innocent, but when it fails it prints both values, and that links the number formatting code. We use a plain `assert!` with a fixed message.
- **Lists are opt-in.** The list machinery sits behind a trait object, so a like button does not pay for rows it does not have.
- **The usual compiler flags.** `lto`, one codegen unit, `panic = "abort"`, and `wasm-opt -Oz` on top. One surprise: `opt-level = "z"` made the file smaller and the _compressed_ file bigger, so we kept the default.

There is also a build without wasm-bindgen at all: plain `extern "C"` functions and numbers. It drops the 2 KB of glue and one more kilobyte of Wasm.

## The todo list

The problem with a CSS-centric framework is dynamic apps. CSS can restyle an element, move it, hide it. It cannot create one. So if the size of your list is not fixed, doing it with CSS alone is almost impossible.

A good demonstration is a todo list, the thing you typically build to battle-test a framework. Let's try this out.

  style={{ width: '100%', height: 460, border: '1px solid #ccc', borderRadius: 8 }}
/>

Type something, press Enter, tick a box. The slider under the list works as before: drag it back and the list goes back in time, titles included.

To make a CSS todo list possible in our worlds, we need to extend the framework with a few new abilities.

### Text

The next problem is text. We've ignored it for a while, but this is where the dynamics we mentioned before start shooting us in the foot. A title is whatever the user typed. It is not a number, and no stylesheet knows it in advance.

Technically CSS can print a string from an attribute. But generated content cannot be selected or copied, and a todo you can't copy is a sad todo. So this time there is no way around it: we need to mutate the HTML.

Here is how. First, an input can carry text. One word in the declaration, and the field's value travels with the event, once, as bytes:

```rust
inputs { add: text => Add, toggle: index => Toggle }
```

Press Enter, and `Add("buy milk")` lands in the log. Now the trick: the projection still carries only numbers. The title's number is the place of that event in the log.

```rust
// item.id is where its Add event sits in the log
.set(ui::item::title.at(row), item.id as f64)
```

So the patch says "row 0, title, 7". The shim asks Rust for the text of event 7 and writes it into the row as a real text node:

```js
row.querySelector('[data-text="title"]').textContent = app.text(7)
```

The string crosses the border on the way in, with the event, and on the way out, when a row has to show it. Everything in between is numbers. And the slider gets the titles for free. The text lives in the log, so going back in time brings the right words back.

### New rows

After the text is saved, we need a new element to put it in. We do it in a quite standard way, in the JS shim. The page carries a `<template>` with one row in it:

```html
<ul>
  <template data-fold="item">
    <li class="item">
      <label>
        <input class="check" type="checkbox" data-checked="done" data-on="click:toggle">
        <span class="title" data-text="title"></span>
      </label>
    </li>
  </template>
</ul>
```

On the Rust side a row is a family of slots, and nothing more:

```rust
family item { class present; checked done; attr n: int; text title; }
```

Note what is missing: there is no "create a row" command. Rust just keeps projecting numbers: "row 3 is present, its number is 4, its title is event 12". When a patch names a row the shim has never seen, the shim makes one:

- It collects everything the patch says about the new row: classes, attributes, the title.
- It renders the row from the template as a string, with those first values already in it.
- All new rows of one patch go in with a single `insertAdjacentHTML`. A thousand rows is one parse, not a thousand clones.
- It remembers the element under its row number, so later writes go straight to it.

The title is the exception. It is set as text after the row is in, never as HTML, so a todo called `<script>` stays a todo.

Rows are never removed. A row the state no longer mentions loses its `present` class, and the stylesheet hides it.

### The checkbox

The second place where we touch the HTML is the checkbox. Its state is a property of a native element, not something CSS can set. So there is a slot for it:

```rust
family item { class present; checked done; attr n: int; text title; }
```

The shim writes `checked` on the input marked `data-checked="done"`, and the look comes back to CSS through [`:checked`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:checked):

```css
.item:has(.check:checked) .title { text-decoration: line-through; }
```

How does Rust know which box was clicked? A click carries the row's index with it. That is what `toggle: index` in the declaration means. Rust flips the item in that row.

<Details withBackground title="A confession about keys">
Our rows are keyed by order. A click says "toggle row 2", and Rust flips the second item. This only works for our app because we never remove an item and never insert one in the middle.

The moment we do, row 2 a minute ago and row 2 now are different todos. Drag the slider under the list into the past, click a checkbox, and the wrong todo gets toggled. The fix is the usual one: give every row a stable key. We even have one for free, the place of its `Add` event in the log. Hello, React keys.
</Details>

### A row that knows its number

Every todo has a number in front of it. The idea: a row number is pure presentation, so it should never cross the border. Let CSS count.

The first version used a [CSS counter](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Counter_styles/Using_counters). It works, but counters are a chain. Every row's number depends on all the rows before it, so one change near the top restyles everything below.

Then `sibling-index()` reached Baseline: a function that tells an element which child it is. It looked like the perfect fit. Each row knows its own number, no chain.

```css
/* minus one, because the <template> is a sibling too */
.item::before { counter-reset: n calc(sibling-index() - 1); content: counter(n); }
```

So we measured it. On a list of ten thousand rows, appending one more got about four times slower than with the old counter. It looks like the browser re-resolves every sibling when the list changes, which is a chain of its own. The newest CSS function in this post measured worst.

What changed in the end is boring. The row's number became one more number from Rust: an attribute, written once when the row appears and printed as is with [`attr()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/attr).

```rust
family item { class present; checked done; attr n: int; text title; }
```

```css
.item::before { content: attr(data-n); }
```

One extra write per row, nothing after that, and close to the cost of having no numbers at all. The dull solution won.

And that is our second app. Hooray, the TODO list! Or, to be precise, the 90 KB todo list. 29 KB brotlied, to be fair, which is about 2 KB more than the like button. It adds. It ticks. It cannot remove an item, it cannot edit one, and a reload loses everything, because the log lives in memory. That is the whole feature list.

### Time

To make the app work we need one more concept: time. A like button doesn't care what time it is. A robot does.

Rust never reads a clock. Time is just one more event in the log, `Event::Tick { ms: 250 }`, and the page owns the clock. While the state says "running", a small loop on the page appends a tick a few times a second:

```js
if (running) host.frame(1000 / fps)
```

This is why the slider works on Brunhilda too. The same ticks in the same order give the same robot, every time. Even the speed is state: faster and slower are ordinary inputs, like a click on the like button.

### A brain, a studio, a world

To make Brunhilda move, we wrote a small crate for her brain. It is a fold, like everything else here: events in, a state out. Her events are commands (start, dock, stop), senses (a bump, "the human is at this cell") and ticks. That is her whole vocabulary.

The same framework builds the rest: the controls of the studio, and the simulated world - the room, the furniture, me.

But notice something interesting about how our boundary fits the separation of concepts. A good part of this post was about one border: Rust on one side, the page on the other, numbers in between. Rust never touches the HTML. It says what should be shown, as data, and somebody else makes it so.

Brunhilda's brain sits behind exactly the same kind of border. She never touches a motor. Events come in, and what she wants goes out as data: a heading for the next frame, an emergency stop. The world makes it so. She knows nothing about the page, and she does not know that her world is simulated either. She lives in the Matrix! Swap the simulated room for real wheels and her crate does not change. Nobody has tried, to be fair.

So the border we fought with for performance turns out to be the place where the concepts separate anyway. What to do lives on one side, how it gets done on the other. For a UI the other side is CSS. For a robot it is the world.

### Effects

Her emergency stop is an effect, and effects deserve a post of their own. The short version: a fold never does anything. It only says what it wants, as a value: "this request should be in flight", "the motors should be stopped". The host compares that with what is already going on, starts what is missing and writes it down in the log. The answer comes back as one more event. So a network request replays just like a click.

We have all of that, including a networked like button that a fuzzer tried hard to break. But not today.

And that is our third app. Hooray, the ROBOT! Or, to be precise, the 143 KB robot. 45 KB brotlied, to be fair. She cleans. She docks. She stops when told. With the naive policy she still attacks me. That is the whole feature list.

It lands close to vanilla JS, and that is not magic. It does roughly what vanilla does: Rust works out what changed, and the shim makes a handful of writes. There is no tree to compare on the JavaScript side. The price is weight. Compressed, the bundle is twelve times vanilla's, because a Wasm module brings its own allocator, collections and panic messages, as we saw. Memory is about twice vanilla's, because we keep a whole log around.

## Wrapping up

Experiments like this one help you learn new concepts, figure out how modern CSS fits real needs, and find a few interesting use cases along the way.

The spoiler from the beginning holds, too. A fold that looks like a reducer, keys for the rows, a diff that ships only what changed: I ended up rebuilding what our everyday tools already do, just in an interesting shape.

I prototyped the first version with my LLM agents very quickly, and then did tons of iterations to fix bugs and improve things. Along the way I wrote a fuzzer, brought in a bundle analyzer and standardized the way I benchmark the app.
