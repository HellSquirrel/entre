Compare Baseline 2021 with Baseline 2026 on [webstatus.dev](https://webstatus.dev/). A lot has changed. CSS can handle more UI logic, and Wasm has new ways to work with JavaScript values.

My usual stack was still React and a pile of components. I wondered how far Wasm and CSS alone could take me. No virtual DOM, and please, please, no state managers. A good excuse to write a toy framework.

Spoiler: I rediscovered several ideas my usual tools already use. Apparently, changing the programming language does not make me original.

Here is the idea:

- The application logic is written in Rust and compiled to Wasm.
- A small JavaScript adapter, or shim, connects the Wasm module to the page. So much for doing the whole thing in Rust and CSS.
- State changes become values CSS can read, ideally [CSS variables](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascading_variables/Using_custom_properties). Some updates still need DOM changes, as we will see.
- The runtime handles updates to the page. Components describe their state and what should be visible; they do not call a render function themselves.

There are two worlds here. On the Rust side, everything is happy and orderly: types, ownership, events arriving in a neat sequence. On the JavaScript side, there is a page and a user happily increasing the entropy. The shim connects the two.

Here is the route from a click to a CSS value. We will follow it one step at a time:

```
click ──▶ Event::Input { input: Toggle, .. }    appended to the log
                     │
                     ▼ step
              View { liked: true }
                     │
                     ▼ project
        (Slot { Root, "--like-liked" }, 1)
                     │
                     ▼ the diff, then the shim
          :root { --like-liked: 1 }
                     │
                     ▼ stylesheet
     content: if(style(--like-liked: 1): "♥ "; else: "♡ ")
```

### A click becomes an event

The Rust runtime has a host that manages the component. It records inputs from the page or the outside world as events. A button click might look like this:

```rust
Event::Input { key: "post:42".into(), input: Input::Toggle }
```

Rust stores these events in order, forming the log. The shim delivers the inputs from the page, starting with this button:

```html
<button class="like" data-on="click:toggle">like</button>
```

A click makes one call into Wasm. The arguments identify `toggle`, with no row index or text to send.

```js
app.dispatch(id, -1, new Uint8Array())
```

Rust turns the input into `Event::Input { input: Input::Toggle, .. }` and appends it to the log.

### A fold turns events into state

So far, I have built a button that keeps a diary. To make it do anything visible, we need to turn that history into state.

We get state by _folding_ the log: going through the events in order and updating the state at each step. This is a [left fold](https://en.wikipedia.org/wiki/Fold_(higher-order_function)), like JavaScript's `reduce` or Haskell's `foldl`.

A log and a fold. That is the idea, and all the effort I put into the name: [LogFold](https://github.com/HellSquirrel/log-fold).

The step function takes the current state and one event, then returns the next state. We call this state `View` because it holds what the component needs to show. For the like button, that is a single flag:

```rust
pub struct View {
    pub liked: bool,
}

pub fn step(v: View, _: u64, ev: &Ev) -> View {
    match ev {
        Event::Input { input: Input::Toggle, .. } => View { liked: !v.liked },
        _ => v,
    }
}
```

The `u64` in the middle is the event's position in the log. The like button doesn't need it, so it's ignored.

Hello, Redux 👋 Except here, keeping the history is part of the runtime's job.

We can throw the state away and rebuild it from the log. Almost: checkpoints add a catch, which we will get to later. Keeping the event history this way has a name: [event sourcing](https://martinfowler.com/eaaDev/EventSourcing.html).

The `View` in this example holds the state needed by the like button. There are no stores with global state. Each view is its own fold over the same log. Two views can run separately, or `zip` can combine their folds into one pass.

### State becomes CSS values

To connect that state to the page, we declare a component. I was trying something different and ended up back at components, just like the ones I usually write in JavaScript.

```rust
logfold_core::component! {
    pub mod ui;
    domain Like;
    prefix like;
    inputs { toggle => Toggle }
    root { var liked: int; }
    state View;
    step = step;
    project = project;
}
```

The declaration connects the inputs, state and functions. For now, the part we need is `project`:

```rust
pub fn project(v: &View) -> Projection {
    Projection::new().set(ui::liked.slot(), u8::from(v.liked))
}

// simplified: the real one is sorted and batches writes
pub struct Projection {
    pairs: Vec<(Slot, f64)>,
}

// what ui::liked.slot() is for our button
Slot { target: Target::Root, kind: SlotKind::Var, name: intern("--like-liked") }
```

`project` converts the state into a list of pairs. That list is the projection. Each pair contains:

- A slot: a named output on the page. Here, `ui::liked` is generated from `root { var liked: int; }`. A typo in its Rust name becomes a compile error.
- A number: for our boolean state, either 1 or 0.

The slot describes where and how to apply the number. For the like button:

- `target` is `Root`, the `<html>` element itself. A named target would be an element with `data-fold="name"`.
- `kind` is `Var`, so the number becomes a CSS variable.
- `name` is `--like-liked`: the component's prefix plus the slot's name. `liked` is a popular word, and a component usually lives on somebody else's page.

The host keeps the last projection it sent and compares it with the new one. It sends only the changed pairs to the page. These make up the patch. For the like button, it contains one pair. The component does not need to request a render; the host applies the patch.

Both the slot and its value travel as numbers, so we do not have to convert names on every click.

The patch sets `--like-liked: 1` in a stylesheet. With constructable stylesheets, the like update changes only the CSS object model, or CSSOM: the shim owns a `:root {}` rule and writes the variable there. No nodes, classes or attributes change. The stylesheet handles the appearance:

```css
.like {
  scale: calc(1 + var(--like-liked) * .1);
  color: if(style(--like-liked: 1): #d32f2f; else: #222);
}
.like::before {
  content: if(style(--like-liked: 1): "♥ "; else: "♡ ");
}
```

Arithmetic with [`calc()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/calc) for the scale, `if()` for the rest. The variable is read right where it is needed, with no selector for the state at all. In our tests, its cost was roughly similar to a plain class selector. Rust never sees a heart. It doesn't know what `liked` looks like, and it shouldn't.

There is a browser-support limit: `if()` is Chromium-only today. In other current browsers the demo falls back to a style query on the same variable, which was a bit slower in our tests:

```css
@container style(--like-liked: 1) {
  .like { color: #d32f2f; }
  .like::before { content: "♥ "; }
}
```

<Details withBackground title="What actually crosses, and where it lands">
Every change is five numbers: which element, which row, what kind, which name, what value. A click on the like button sends exactly this:

```js
[0, -1, 0, 1, 1]
// element 0 is "root", -1 is "no row", kind 0 is a variable, name 1 is "--like-liked", value 1 is "on"
```

The shim fetches each name once and caches it. At startup, it creates a stylesheet with one empty rule. Root variables are written into that rule:

```js
const sheet = new CSSStyleSheet()
sheet.replaceSync(':root {}')
document.adoptedStyleSheets.push(sheet)

sheet.cssRules[0].style.setProperty('--like-liked', 1)
```

This is a write to the CSS object model, not to the document. In our measurements it was about as cheap as toggling a class. The generated stylesheet registers the variable, so it has a type and a default:

```css
@property --like-liked { syntax: "<integer>"; inherits: true; initial-value: 0; }
```

A named target can receive variables through a rule on its class, without the shim looking up an element. Repeated rows carry their values on the elements themselves.

The history panel still updates its own DOM after a click. Browsers without constructable stylesheets also use a fallback that writes root variables to `<html>`'s inline style. So the like action leaves the DOM alone when it uses a constructable stylesheet; the history panel and the fallback still change it.
</Details>

Rust's description of the page is a flat list of slot-value pairs. The HTML structure and appearance stay on the browser side.

## Challenges

Even a like button raised two questions: how much does crossing between Rust and JavaScript cost, and why is the bundle so large?

### The border

The boundary between Rust and JavaScript sounds expensive. In our measurements, small numeric calls were cheap; converting strings took more work.

Rust's ordinary data structures live in Wasm's linear memory, an array of bytes. JavaScript can access those bytes through typed-array views. JavaScript objects, including DOM nodes, live elsewhere. Rust can keep handles to them, but their contents do not become Rust data. Here is what matters for our framework:

- Numbers need no string encoding or object serialization. That suits our numeric patches.
- Converting between a Rust `String` and a JavaScript string copies and re-encodes the contents: Rust uses UTF-8, while JavaScript exposes UTF-16 code units. Keeping a reference to an existing JS string avoids that conversion.
- Wasm can receive a host value as an `externref`. With wasm-bindgen, Rust stores a handle to that value; calling its JavaScript methods still involves host calls.
- Calling the DOM from Rust does not bypass the browser's DOM, style or layout work. Rust does not get a secret faster DOM.

<Details withBackground title="A detour: JS string builtins and Rust">
Wasm 3.0 brought [JS String Builtins](https://developer.mozilla.org/en-US/docs/WebAssembly/Guides/JavaScript_builtins). Holding a JavaScript string as an `externref` was already possible. The new part is working on it through functions from the reserved `wasm:js-string` namespace: `length`, `concat`, `substring`, `equals`. The engine recognizes these imports and can optimize them without an application-written JavaScript wrapper. Reading a JS string's length needs no conversion to UTF-8. Creating or concatenating strings can still allocate.

```js
WebAssembly.instantiateStreaming(fetch('app.wasm'), imports, {
  builtins: ['js-string'],
  importedStringConstants: 's',
})
```

```wasm
(global $liked (import "s" "liked") externref)
(func $equals (import "wasm:js-string" "equals")
  (param externref externref) (result i32))
```

The second option, `importedStringConstants`, is particularly neat. The engine reads the import name and supplies it as a JavaScript string. The literal still appears in the module's import metadata, but it does not need a UTF-8 copy in linear memory.

Rust can already keep a JS string without copying its contents through [`js_sys::JsString`](https://wasm-bindgen.github.io/wasm-bindgen/reference/types/str.html). Rust holds a numeric handle, and the actual reference lives in a table. Those handles can live in structs and vectors. A `Vec<JsString>` is perfectly legal; a `Vec` of bare Wasm references is a different matter.

Our current pipeline does not use the new builtins. With wasm-bindgen 0.2.128 and the corresponding js-sys 0.3.105 release, the ordinary [`JsString` bindings](https://github.com/wasm-bindgen/wasm-bindgen/blob/0.2.128/crates/js-sys/src/lib.rs) call JavaScript properties and methods. Using `wasm:js-string` imports would take extra integration. The handles themselves do not prevent this: Wasm can look up a reference in its table and pass it to a builtin. I had only meant to build a like button.

</Details>

For now, LogFold takes the straightforward route: the log keeps Rust-owned text, so its core can run outside a JavaScript host too. Names are fetched and cached by the shim, and patches carry numeric IDs. Text the user typed enters the log as UTF-8 bytes; a text patch carries the event's position, and the shim asks for a JavaScript string when a row needs to show it. That conversion still costs us. That is a tradeoff I chose for LogFold.

### The bundle

Then there is the bundle size. Compiling Rust to Wasm still brings along support code. These builds have no garbage collector, but they still include an allocator, panic support and collections. Here is what makes up the like runtime, counting the files listed above and compressing with Brotli quality 11 (decimal KB):

```
the Wasm module         19.01 KB
the JS shim              5.79 KB
wasm-bindgen glue        2.27 KB
the generated CSS        0.10 KB
                        --------
                        27.17 KB
```

That is 27 KB compressed, or 84 KB uncompressed, for a like button I could write in a few lines of JavaScript. Earlier [twiggy](https://rustwasm.github.io/twiggy/) profiles of named, uncompressed Wasm builds pointed at the host and exports, framework machinery, collections, panic formatting and the allocator. Those profiles describe the Wasm module, not shares of the compressed total above.

The like-button logic is a tiny part of its own bundle. Most of the weight is the machinery we brought along to flip one flag. The exact percentages change between builds. It is still a lot of code for a heart.

I tried a few ways to reduce that overhead:

- **Swapped the allocator.** In our earlier Wasm build, the default allocator, dlmalloc, contributed about 8 KB of uncompressed code. Our apps allocate small, short-lived things, so we use [talc](https://github.com/SFBdragon/talc), which contributed about half of that in the measured build.
- **Threw out the standard sort.** In an earlier build, one call to `sort` added about 17 KB to the uncompressed Wasm module. A hand-written merge sort costs a fraction of that.
- **Less formatting.** `assert_eq!` looks innocent, but when it fails it prints both values, and that links the number formatting code. We use a plain `assert!` with a fixed message.
- **Lists are opt-in.** The list machinery sits behind a trait object, so a like button does not pay for rows it does not have.
- **The usual compiler flags.** `lto`, one codegen unit, `panic = "abort"`, and `wasm-opt -Oz` on top. One surprise: `opt-level = "z"` made the file smaller and the _compressed_ file bigger, so we kept the default.

<Details withBackground title="The build without wasm-bindgen">
There is also a build without wasm-bindgen at all: plain `extern "C"` functions and numbers. The current raw Wasm module is 52.18 KB uncompressed and 17.85 KB Brotli, versus 54.74 KB and 19.01 KB for the bindgen module. It also needs no generated bindgen JS, which is another 2.27 KB Brotli in the normal build. These are module and glue comparisons; the raw path has its own loader, so they are not whole-page totals.
</Details>

This needs three additions to the framework: text inputs, new rows and native checkbox state.

### Text

A todo title can be anything the user types. The stylesheet cannot know it in advance, and our projection currently contains only numbers.

CSS can display a string from an attribute, but generated content does not offer the same reliable selection and copying as ordinary text. I would like to be able to copy my shopping list. We need a real text node.

An input can carry text. Adding `text` to its declaration tells the host to include the field's value as bytes:

```rust
inputs { add: text => Add, toggle: index => Toggle }
```

Press Enter, and `Add("buy milk")` is appended to the log. The projection can still contain only numbers: the title slot stores the position of that event.

```rust
// item.id is where its Add event sits in the log
.set(ui::item::title.at(row), item.id as f64)
```

So the patch says "row 0, title, 7". The shim asks Rust for the text of event 7 and writes it into the row as a real text node:

```js
row.querySelector('[data-text="title"]').textContent = app.text(7)
```

The text crosses into Rust with the input and returns as a JS string when a row needs to display it. The patches carry only its event index. Because the host retains the text, either in the log or its archive, historical views can display the original titles too.

### New rows

Next, the shim needs an element for the new item. The page provides a `<template>` containing one row:

```html
<ul>
  <template data-fold="item">
    <li class="item">
      <label>
        <input class="check" type="checkbox" data-checked="done" data-on="click:toggle">
        <span class="title" data-text="title"></span>
      </label>
    </li>
  </template>
</ul>
```

Rust describes the rows as a family of slots:

```rust
family item { class present; checked done; attr n: int; text title; }
```

There is no separate "create a row" command. Rust projects numbers: "row 3 is present, its number is 4, its title is event 12". When a patch names a row the shim has never seen, the shim makes one:

- It collects everything the patch says about the new row: classes, attributes, the title.
- It renders the row from the template as a string, with those first values already in it.
- All new rows of one patch go in with a single `insertAdjacentHTML`. A thousand rows is one parse, not a thousand clones.
- It remembers the element under its row number, so later writes go straight to it.

We add the title as text after inserting the row, so a todo called `<script>` stays a todo.

In this todo list, rows are never removed. A row the state no longer mentions loses its `present` class, and the stylesheet hides it.

### The checkbox

The checkbox also needs a DOM update. Its `checked` state is a native element property that CSS cannot set. We give it a slot of its own:

```rust
family item { class present; checked done; attr n: int; text title; }
```

The shim writes `checked` on the input marked `data-checked="done"`, and CSS reads that state through [`:checked`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:checked):

```css
.item:has(.check:checked) .title { text-decoration: line-through; }
```

The click also carries the row's index, as specified by `toggle: index` in the declaration. Rust uses it to toggle the corresponding item.

<Details withBackground title="A confession about keys">
Our rows are identified by position. A click says "toggle row 2", and Rust flips the third item: indices start at zero. This works for our app because we never remove an item or insert one in the middle.

If you click while viewing the past, the action still goes at the end of the log and the page jumps back to the present. It does not create a new branch of history. If we allowed removals or insertions in the middle, row 2 in the past could be a different todo from row 2 now, and we could toggle the wrong one. The fix is the usual one: give every row a stable key. We even have one for free, the place of its `Add` event in the log. Hello, React keys.
</Details>

### A row that knows its number

Every todo has a number in front of it. I thought CSS could handle that for me, but `sibling-index()` made appending a row slower in our Chrome test. In the end, Rust supplies the number as an attribute and CSS displays it with [`attr()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/attr). The dull solution won.

<Details withBackground title="How CSS lost the counting job">
The first version used a [CSS counter](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Counter_styles/Using_counters). It works, but the numbering depends on what came before. A change near the top can make the browser recalculate the numbers below it.

Then `sibling-index()` reached Baseline: a function that tells an element which child it is. It looked like the perfect fit. Each row knows its own number, no chain.

```css
/* minus one, because the <template> is a sibling too */
.item::before { counter-reset: n calc(sibling-index() - 1); content: counter(n); }
```

So we measured it in Chrome. On a list of ten thousand rows, appending one more got about four times slower than with the old counter. So much for my assumption that each row could handle this independently. The newest CSS function in this post came last in this test.

In the end, Rust supplies the row number too. The shim writes it to an attribute when the row appears, and CSS displays it with [`attr()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/attr).

```rust
family item { class present; checked done; attr n: int; text title; }
```

```css
.item::before { content: attr(data-n); }
```

This adds one write when a row appears and no further numbering updates for our append-only list. In this test, the cost was reasonably close to having no numbers at all.
</Details>

And that is our second app. Hooray, the TODO list! Or, to be precise, the 92 KB todo runtime. 30 KB brotlied. Using the same counting rules, that is about 2.4 KB more than the like runtime before rounding. It adds. It ticks. It cannot remove an item, it cannot edit one, and a reload loses everything, because the log lives in memory. That is the whole feature list.

## How much history can we keep?

The first version kept every event forever. The runtime could still reach all that memory. I had just told it to remember everything. A memory leak with excellent record keeping.

Keeping up with new events is cheap: we apply each one to the current state once. Going back in time takes more work. We do not want to read the whole log from the start every time we move the slider.

That is where checkpoints help. We save the state after `k` events, then continue from there with the remaining events and their original indices. Because the fold is deterministic, we get the same result:

```
fold(log) == fold_from(state_at(k), log[k..])   // for any k
```

We can also throw away the events before a checkpoint. But then we have to keep that checkpoint. We need it and the remaining log to rebuild the state. The slider cannot visit the forgotten past, and a new fold cannot read events we no longer have. Time travel has a retention policy.

Text needs special treatment too. In our todo list, a title refers to the event that supplied its text. Before deleting such an event, we move the text into a separate archive. That archive can keep growing, as can the app's state and the rows we hide rather than remove. This limits the event history, but other memory use can still grow.

<Details withBackground title="What if there are many folds?">
We zip them all together before we go. `zip` runs two folds over the same events in one pass and keeps a pair of states, so a checkpoint is always the state of _one_ fold. Views derived with `map` need no separate checkpoint: they are functions of that state.
</Details>

<Details withBackground title="Time travel between checkpoints">
Checkpoints live in a B-tree, ordered by event position. To show a past state, we find the nearest checkpoint at or before that position, then replay the remaining events. This is how the slider shows the past.

A small Wasm lesson. In an earlier build, checkpoint cleanup pulled extra tree-removal code into the Wasm module through a single call to `BTreeMap::remove`. To shrink the module, we had to stop calling that method. Instead of removing old checkpoints, we now rebuild the tree from the ones we keep. Same retained checkpoints, less machinery to ship.
</Details>

For something more complicated, I borrowed a problem from my daily life. I have a robot vacuum cleaner lurking in my apartment, and she tries to sweep me up whenever I am in her way. I am fond of her anyway. She has a strong character, so she got a strong name: Brunhilda.

The next app simulates this arrangement: Brunhilda sweeping the apartment, the furniture standing in her way, and me walking around.

### Time

To make the app work we need one more concept: time. A like button doesn't care what time it is. A robot does.

Rust never reads a clock. Time arrives as another event in the log, `Event::Tick { ms: 250 }`, and the page owns the clock. While the state says "running", a small loop on the page advances the simulation a few times a second:

```js
if (running) host.frame(1000 / fps)
```

`frame(250)` advances virtual time by 250 ms. The log stores the total elapsed time in `Tick.ms`: 250, 500, 750, and so on. Frames also record what the simulated sensors report.

This is why the slider works on Brunhilda too. Replaying the commands, sensor reports and ticks in order gives us the same robot state. Even the speed is state: faster and slower are ordinary inputs, like a click on the like button.

### A brain, a studio, a world

To make Brunhilda move, we wrote a small crate for her brain. It is a fold, like everything else here: events in, a state out. Her events are commands (start, dock, stop), sensor reports (a bump, "the human is at this cell") and ticks. That is her whole vocabulary.

The same framework builds the rest: the controls of the studio, and the simulated world - the room, the furniture, me.

The separation is similar to the one between Rust and the page. Rust describes what should be visible as data; the browser host applies it.

Brunhilda's brain works the same way. Events come in; a heading or an emergency-stop request comes out as data. The host acts on it. Her brain knows nothing about the page or the simulation. She lives in the Matrix!

In principle, a host for real wheels could keep the same brain crate, as long as it uses the same sensor and movement model. I have not tested that. My furniture has suffered enough.

I worried that this boundary would slow things down, but it also helps organize the code. The component says what should happen, and the host makes it happen. That works for both a page and a simulated robot.

### Effects

Her emergency stop is an effect. The full design needs its own post, but the basic idea is simple. A fold never performs the effect itself. It only says what it wants, as a value: "this request should be in flight", "the motors should be stopped".

The host compares that with what it has already started and records a `Started` event before starting the effect. If the effect has an answer, that comes back as another event. The emergency stop is fire-and-forget; it has no answer to wait for.

Replay uses the recorded events to rebuild state. It does not send the request again. Dragging a slider should not accidentally order a second pizza.

This was also where testing the behavior mattered. I built the first prototype quickly with my LLM agents, then spent much longer fixing bugs and refining it. Along the way, I used a bundle analyzer, made the benchmarks more consistent and wrote a fuzzer.

The fuzzer tests a networked like-button model against a simulated server, trying to break the effects logic. That model still needs code to send real network requests. I will leave that for another post.

And that is our third app. Hooray, the ROBOT! Or, to be precise, the 144 KB robot runtime. 46 KB brotlied, with the same counting rules and its imported manifest included. She cleans. She docks. She stops when told. With the naive policy she still attacks me. That is the whole feature list.

## So, how fast is it?

I also wanted to compare the runtime with vanilla JS and React. These tests cover a few table operations, only a small part of what a full framework does.

I used [js-framework-benchmark](https://github.com/krausest/js-framework-benchmark), which creates, updates, swaps and clears table rows.

The benchmark expects real text in the table. So LogFold uses a separate adapter for this benchmark in place of its usual shim. Rust still produces numeric patches; the adapter writes text and manages rows. The results below measure Rust and this adapter together. The demos use CSS differently, so these numbers do not tell us how fast that part is.

I ran the benchmark's own driver on my laptop.<sup><a href="#benchmark-machine" id="benchmark-machine-ref" aria-label="Benchmark machine details">1</a></sup> These are median times in milliseconds, alongside the vanilla JS reference and React 19.2 hooks entry:

## Wrapping up

This is still a long way from a full-featured framework. Three demos and a robot with questionable manners do not quite get us there. But the results are promising.

The approach turned out to be less crazy than I expected. Performance looks good in the tests so far, and the bundle sizes seem acceptable for the experiments I want to build next. I say this after spending several paragraphs making fun of my own like button.

I also found myself enjoying writing components in Rust. I think I will keep playing with it and see how it goes.
